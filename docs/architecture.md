## 1. 問題與目標

實驗室目前以共用試算表登記 GPU，依各人填寫的緊急程度協調。大家傾向保留整台機器，
原因是大部分工作不是「提交後等結果」的批次工作：開發時要反覆測試，AI coding 工具每隔幾秒就要執行程式，
agent 開發需要隨時呼叫模型。

- **G1** 把多台異質機器視為同一個資源池，使用者不必自己挑機器。
- **G2** 不保留機器也能完成三種工作，而且比保留機器更方便；否則使用者會回到試算表登記。
- **G3** 排程決策可以解釋：誰在用資源、工作為什麼在等、排程器做了什麼決定。
- **G4** 作為 OS 課程專案，展示排程、資源配置、隔離、程序控制與故障處理。

第一版不包含（沿用 plan.md）：跨節點分散式訓練、同一張 GPU 切給多個工作、Scheduler 高可用、通用程序 checkpoint。
其中 Scheduler 所在節點的故障處理列為最後可以做的擴充，見第 12 節。

## 2. 工作類型

| | 訓練（批次） | 快速測試 | Agent 開發 |
|---|---|---|---|
| 發起者 | 使用者透過 CLI | AI coding 工具，每隔幾秒一次 | agent 程式透過 HTTP |
| 執行時間 | 數小時到數天 | 數秒到數分鐘 | 單次請求數秒；服務持續運行 |
| 最在意 | 公平、等待時間 | 延遲，要接近本機執行 | 冷啟動時間與可用性 |
| GPU | 整張獨占 | 短期租用，用完歸還 | 多人共用同一個模型服務 |
| 機制 | 批次佇列、優先權、公平性、backfilling | session lease（快車道） | 推論 Gateway、按需啟動、閒置回收 |
| 階段 | M3～M8、M11 | M9 | M10 |

長時間互動開發（Jupyter、debugger 長時間占用 GPU）是否支援仍未決，見 Q2。

## 3. 系統架構

### 3.1 元件

```text
開發節點（每台機器）                 kayle
  labflux CLI ───── /api ──────►  Scheduler：資源帳（SQLite）、排程迴圈、
  agent 程式 ────── /v1 ───────►             程式快照與輸出、Dashboard、推論 Gateway（M10）
                                      ▲
                                      │ 註冊、心跳、輪詢命令、回報事件／日誌／輸出
Worker（每台機器）────────────────────┘
  Docker 容器 ── 唯讀掛載 ──► 資料集副本（節點本機）◄── 複製 ── 實驗室 NAS（正本）
```

| 元件 | 位置 | 職責 | 狀態 |
|---|---|---|---|
| Scheduler | kayle，單一程序 | API、排程迴圈、資源帳、程式快照與輸出存放、Dashboard | 已實作 |
| 推論 Gateway | Scheduler 內 | `/v1/models`、`/v1/chat/completions` | 已決定（M10） |
| Worker | 每台加入資源池的機器 | 註冊、心跳、領取命令、執行 Docker、回報結果、偵測 GPU | 已實作 |
| CLI（`labflux`） | 每台開發節點 | submit、status、logs、fetch、nodes、cancel | 已實作 |
| Dashboard | Scheduler 的 `/dashboard` | 監控節點與工作 | 已實作 |

### 3.2 通訊（已實作）

- Worker 主動註冊並輪詢命令；心跳由獨立執行緒每 2 秒送出。超過 10 秒沒收到心跳，節點變成 `OFFLINE`，
  未確認停止的工作變成 `UNKNOWN`，配置保留。
- 命令有唯一 ID，可安全重送；舊 attempt 的回報不會改寫目前狀態。
- 事件、日誌與輸出先寫入 Worker 本機的 outbox，再上傳。
- 使用者 API 以使用者 token 驗證；`/internal/workers` 使用獨立的 Worker token。
- M9 起，命令改由長連線通知、原本的 API 領取，輪詢只留作備援（見第 8 節 T4）。

### 3.3 部署（已實作）

- 使用專用帳號 `labflux`（兩台 UID／GID 相同，docker 群組，只允許金鑰登入），以 systemd user unit 加 linger 執行。
- kayle 執行 Scheduler 與 Worker；karma 執行 Worker。kayle 的防火牆只允許 karma 與本機連到 Scheduler。
- 真實 IP、GPU UUID 與帳號名稱只放在 Git 忽略的 `configs/local-lab.toml` 與 `.labflux/lab/`；
  文件一律使用 `192.0.2.0/24` 範例值。

### 3.4 機器現況

| | kayle | karma |
|---|---|---|
| 角色 | Scheduler、Worker、開發節點 | Worker、開發節點 |
| GPU | RTX 3090、RTX A5000（驅動 535，只能用 CUDA 12.x 映像） | RTX 4090（驅動 580） |
| 交給 LabFlux 的上限 | CPU 16、RAM 48 GiB | CPU 16、RAM 24 GiB |
| 網路 | 1GbE | 1GbE |
| 實驗室 NAS | 已掛載 | 未掛載（NAS 的 export 沒有包含 karma 目前的位址） |
| `/datasets` | 獨立磁碟 | 與系統同一個分割區 |

plan 7.8 要求至少三個異質節點，目前只有兩台實體機，見 Q8。

## 4. 需求與規格

### 4.1 資源與隔離

- **R1** CPU 以配額限制；RAM 為硬上限且不使用額外 swap；透過 Docker 設定 cgroups。（已實作）
- **R2** GPU 整張分配，以 UUID 指定容器可見的裝置；CPU 工作看不到任何 GPU。（已實作）
- **R3** GPU 需求可指定數量、型號與每張最低 VRAM；符合條件的卡中，VRAM 較小的優先。（已實作）
- **R4** 有運算程序或已用 VRAM ≥ 1 GiB 的卡視為外部使用，不接受新配置。（已實作）
- **R5** 配置資源後才派送；確認容器終止後才釋放。（已實作）
- **R6** 每台機器以 `allocatable_*` 劃出交給資源池的部分，其餘留給在該機器上工作的人。（已實作；數值見 3.4）

### 4.2 工作生命週期與故障處理

- **R7** 每次執行有獨立的 attempt；重跑建立新 attempt，保留舊紀錄。（已實作）
- **R8** Worker 失聯時工作標為 `UNKNOWN`；確認舊容器已終止或節點已停機，才允許重跑。（標記已實作；重跑為 6.5，已決定）
- **R9** Worker 重啟時接手仍在執行的容器，不停止工作。（已實作，M6.4）
- **R10** Scheduler 重啟後從資料庫還原，完成 Worker 狀態核對才恢復派送。（已決定，M6.6）
- **R11** 每個工作有硬性執行時限，預設 1 小時。（已實作）

### 4.3 排程

- **R12** 嚴格 FCFS 作為比較基準。（已實作）
- **R13** 批次分數 = 優先權 × 100 + 累積排隊分鐘 − 近 60 分鐘資源占用分鐘；優先權 0～9，預設 5。（已決定，M8）
- **R14** EASY backfilling：依硬性時限計算隊首的保留時段，只讓不會延後隊首的工作先跑。（已決定，M8）
  隊首有保留時段時，先跑的工作優先拿隊首用不到的卡，即使那張卡比另一張空卡大（只在這種情況下蓋過 R3 的小卡優先）。
  執行中的 session 以目前的 lease 到期時間計入（見 T9）。
- **R15** 互動工作（快速測試、模型服務）排在批次工作之前。（已決定，M9.5）
- **R16** 依資料集位置與頻寬排程（delay scheduling），見 7.1。（提議；方向已認可）
- **R17** 保留一部分容量給互動工作。（提議，見 Q1）
- **R18** 搶占只作用於同時標記 `restartable` 與 `preemptible`、且優先權較低的批次工作；確認停止後才釋放；
  預設最多重新啟動 3 次。（已決定，M11）

### 4.4 可觀察性

- **R19** 只透過 Dashboard 與 CLI，就能說明誰在用資源、工作為何等待，以及排程器做了什麼決定，
  包含資料集複製進度與等待副本的原因。（部分已實作；完整為 M12）

## 5. 開發節點與程式碼

已決定（2026-11-06）：

- **D0** 每台機器都可以用來開發：在本機開工作目錄、照常做事；只有工作交給 LabFlux。
- **D3** 程式在機器之間用 git 移動。LabFlux 不做開發機之間的同步，也不共享家目錄：
  同一位使用者在不同機器的 UID 不同，放在 NAS 上共用會造成檔案擁有者錯亂。
- **D3a** 使用前提：同一個專案同時只在一台機器上修改，修改的主要是 AI coding 工具。
- **D4** 工作使用送出時打包的不可變快照（已實作 `--source`）。工作在排隊、重跑、被搶占後重新開始時，
  都跑同一版程式；快照存在 Scheduler，所以重跑可以排到任何一台。
- **D4a** 一個工作只帶五樣東西：程式快照、執行環境（映像，或 `pyproject.toml` 加 `uv.lock`）、
  資料集名稱、參數與環境變數、資源需求。開發機上的絕對路徑、被忽略的本機檔案、shell 環境變數與本機 `.venv`，
  工作都看不到；所以從哪台送出，結果都一樣。
- **D10** 檔案系統的設計只用於資料集（路線 1），程式不放進 LabFlux 的檔案系統。
  讓程式也放進同一套檔案系統（路線 2）列為擴充，見 E2。

已決定（2026-11-15，快速測試的工作目錄同步）：

- **D4b** 去程：每個被送到遠端的指令執行前，先送一份完整快照（打包規則與 `--source` 相同：依 `.gitignore`、
  `.labfluxignore`，排除 `.git`、`.venv` 等），套用到 session 的工作目錄：快照裡的檔案直接覆蓋；
  上一份快照有、這一份沒有的檔案跟著刪除（避免 import 到已刪除的舊檔）；指令自己產生的檔案與 `.venv` 保留。
  實測 1.4 MB 的 repo 打包、傳輸、解壓共約 0.1 秒，所以先不做只送變動檔案的增量同步；repo 大到明顯變慢時再考慮。
  `pyproject.toml` 或 `uv.lock` 和上一次不同時，先在 session 執行 `uv sync`，再執行指令。
  專案裡的 symbolic link 不放進快照，也不跟著連結去讀內容，每個指令提示一次；連結指向的資料集要改用 LabFlux 的資料集（第 7 節）。
- **D12** 回程（寫回）：每個指令結束後，把這次新增或修改的檔案送回本機的同一個位置。不寫回的話，
  程式在遠端寫出 `results.json`，AI 接著在本機讀它（T2）會找不到，可能誤以為程式失敗而去改程式。
  - 指令開始前記錄工作目錄內每個檔案的大小與修改時間，結束後比對；`.venv`、`__pycache__`、`.pytest_cache` 等快取不送。
  - 每個指令的寫回總量上限預設 100 MB（實測後調整），檔案數上限與封存檔相同（預設 10000 個）；
    超過的檔案（例如 checkpoint）留在遠端，記錄與提示方式見 T11。
  - 本機同一個檔案在指令執行期間也被改過時不覆蓋，改存成 `<檔名>.remote` 並提示。依 D3a，而且指令執行時 AI 在等結果，這種情況很少。
  - 對應 AFS 的 close-to-open 一致性：AFS 在檔案關閉時寫回，這裡在指令結束時寫回；兩邊都不做持續的雙向同步。
  - session 結束時遠端工作目錄刪除；留在遠端的大檔要保留，需寫到 `/outputs`（session 結束時上傳，見第 6 節與 T11）。
    跨 attempt、跨 session 保留的 checkpoint 見第 6.1 節的 `/persist`。

提議（待確認）：

- **D1** 開發節點是寫程式的地方，不是直接使用 GPU 的地方；GPU 一律透過資源池取得。
- **D2** 每台機器都可以當開發節點：裝好 CLI，每位使用者有自己的設定檔
  `~/.config/labflux/config.toml`（權限 600，內含 Scheduler 位址與個人 token）。
  CLI 目前已支援 `--config` 與 `LABFLUX_CONFIG`，預設路徑是新增項目。
- **D11** 補上快照的三個缺口：專案依賴目錄外的程式（例如 `path = "../mylib"`）會帶不到；
  專案裡的 `data/` 預設被排除；同一份快照送出多個工作時會重複上傳，可以先用 sha256 詢問 Scheduler。
- **D5** 程式只從開發節點單向送到 Worker。批次工作的結果透過 stdout／stderr、exit code 與 `/outputs` 取回；
  快速測試另外在每個指令結束後寫回變動的檔案（D12）。兩者都不做持續的雙向同步。
- **D6** 快速測試指令 `labflux run --gpu 1 -- python test.py`：第一次自動租用 session，之後續租；
  輸出即時串流，exit code 原樣回傳，Ctrl-C 轉成取消（取消的範圍已決定，見 T10）。專案的 `CLAUDE.md`／`AGENTS.md` 註明 GPU 測試要用這個指令。
- **D7** 有人直接使用 GPU 時，依 R4 該卡自動退出資源池。無法阻止有人直接使用已配置給工作的卡
  （要改 `/dev/nvidia*` 權限，會影響所有人），只能靠使用規範與 Dashboard 顯示外部使用。
- **D8** session 優先排在發起指令的那台機器上（同步程式只是本機複製）；該機器沒有空位才排到別台。
- **D9** 只用 CPU 的測試直接在開發節點本機執行，不經過 Scheduler。

直接在 NAS 目錄上執行工作的模式不在路線 1 內：它會讓工作讀到排隊後才改過的程式，違反 D4。
如果之後要讓程式放在共用的檔案系統上，併入 E2 一起評估。

考慮過但不採用的做法：

| 做法 | 不採用的原因 |
|---|---|
| 程式只放一台機器，從其他機器連過去編輯 | 等於只有一台機器能開發，不符合 D0 |
| 每次存檔都同步到所有機器 | 程式只有 MB 級，傳輸量不是問題；但會帶來一致性、權限與維運成本，而且工作仍然需要快照 |
| Worker 從 git 拉指定的 commit | Worker 需要 repo 的存取權限；還沒 commit 的修改帶不到 |
| LabFlux 自己做開發機之間的同步 | 等於重做一次 git |

## 6. 容器內路徑與檔案

| 路徑 | 用途 | 存放位置 | 權限 | 生命週期 | 狀態 |
|---|---|---|---|---|---|
| `/workspace` | 程式快照、暫存檔 | Worker 本機，每個 attempt 一份 | 讀寫 | 輸出上傳後刪除，保留 `state.json` 等紀錄 | 已實作 |
| `/outputs` | 要取回的結果 | Worker 本機，結束後上傳 Scheduler | 讀寫 | Scheduler 端保留期限未定 | 已實作；期限見 Q9 |
| `/datasets/<名稱>` | 資料集 | 節點副本或 NAS | 唯讀 | 由資料集機制管理（第 7 節） | 依名稱掛載已實作；版本化為提議 |
| `/uv-cache` | uv 套件快取 | Worker 本機，同節點的工作共用 | 讀寫 | 長期保留 | 已實作 |
| `/persist` | checkpoint 與大型輸出，跨 attempt、跨工作保留 | 執行工作的那台節點本機（不經 Scheduler、不需要 NAS） | 讀寫 | 保留到擁有者刪除 | 方向已決定（2026-11-16），細節為提議，見 6.1 |

- **F1** Scheduler 只傳小檔：程式快照 ≤ 100 MiB、輸出 ≤ 1 GiB、每個 attempt 的日誌 ≤ 16 MiB（存在 SQLite）。（已實作）
- **F2** 大檔（資料集、模型權重、checkpoint）不經過 Scheduler。（提議）
- **F3** 封存檔拒絕路徑跳脫、連結與特殊檔案，並限制大小與檔案數。（已實作）
- **F4** uv 模式使用 Python 3.12 + uv 的預設映像，`UV_LINK_MODE=copy`
  （快取與工作目錄是不同的 bind mount，無法建立硬連結）。（已實作）
- **F5** Worker 心跳回報資料目錄所在磁碟的剩餘空間，低於保留量就不接新工作。（提議）
- **F6** uv 快取是否依使用者分開。（未決，見 Q4）

### 6.1 Checkpoint 與大型輸出

已決定（2026-11-16）：

- **P0** checkpoint 與大型輸出留在執行工作的那台機器上，寫進節點本機的磁碟，不經過 Scheduler，也不要求 NAS。
  這是最簡單的做法：寫入速度就是本機磁碟的速度，不佔網路，也不受 karma 還沒掛上 NAS（Q6）影響。
- **P0a** Scheduler 記錄每一份保存的資料在哪台機器：名稱、擁有者、節點、大小、最後使用時間、產生它的工作。
  使用者查得到資料在哪裡，排程器也依這份紀錄決定之後的工作要排到哪台。
- **P0b** 之後可以加入「同步到其他機器」的設計，列為擴充 E3。

以下為提議（容器怎麼寫入、排程怎麼配合），待確認：

- **P1** 以具名的「保存區」為單位。工作設定 `"persist": "mnist-run1"`；Worker 在本機建立
  `<persist_root>/<擁有者>/<名稱>/`，以讀寫方式掛到容器的 `/persist`。程式把 checkpoint 寫到 `/persist/...`。
  和 `/workspace` 不同，attempt 結束時不刪除。
- **P2** 同一個名稱第一次使用時，建立在被排到的那台節點；之後用到同一個名稱的工作（續訓、重跑、搶占後重新開始、
  要讀 checkpoint 的快速測試 session）一律排到那台（硬性親和），因為別台沒有這份資料。
  那台離線或沒有空位時就等待，Dashboard 顯示原因。這和資料集的 L5（重跑排回原節點）同一個想法，但這裡是必須，不是偏好。
- **P3** Worker 在 attempt 結束時與心跳時回報保存區的大小，Scheduler 寫進資料庫。
  `labflux persist ls` 列出名稱、節點、大小與最後使用時間；`labflux persist rm <名稱>` 由 Scheduler 發命令給那台的 Worker 刪除。
- **P4** 同一個保存區同時只給一個工作或 session 寫入，由 Scheduler 記錄，避免兩個工作同時寫壞同一份 checkpoint。
- **P5** 取出檔案不經 Scheduler（F2）：在那台機器上直接讀（容器以 `labflux` 帳號執行，目錄設為其他人可讀），
  或開一個掛同一個保存區的快速測試 session，用 `python` 讀取或把需要的小檔複製到 `/outputs`。
- **P6** 保存區算進節點的磁碟預算（F5）。checkpoint 無法重建，所以超過預算時不自動刪除，只拒絕建立新的保存區並在 Dashboard 警告；
  長時間沒用的保存區列出來提醒擁有者。
- **P7** 節點永久故障時，那台的保存區就不見了。這是「只留在本機」的代價，記為已知限制；重要的結果要另外複製（E3）。

對應的 OS 概念：資料留在產生它的節點（data locality），由中央的中繼資料服務記錄位置（像 HDFS 的 NameNode 記錄 block 在哪台），
排程依位置做親和（affinity scheduling）。

## 7. 資料集

使用者提供的現況：常用資料集約 50 GB；修改多半是補 label、加 CoT；各節點的快取磁碟不是限制。

已實作：Worker 設定「名稱 → 本機路徑」，Scheduler 依名稱配對節點，容器以唯讀方式掛載。

已決定（2026-11-15）：

- **S0** 資料集以「整個版本」為單位複製到節點本機的快取目錄：工作排隊時，就把它需要的版本從正本整份複製到
  預計執行的節點，先寫進暫存目錄、完成後才改名成正式目錄；複製期間不佔 GPU，完成後才派送工作。
  容器以唯讀方式掛載本機目錄。快取超過磁碟預算時，刪掉最久沒用、而且沒有工作在讀的版本（LRU）。
  排程優先選已有副本的節點（7.1）。
- **S0a** 複製資料集時限速，預設約網卡頻寬的 80%，由複製程式自己控制、不需要 sudo；
  讓同一張網卡上的快速測試與心跳不被擠掉。以 1GbE 計算，50 GB 約從 7～8 分鐘變成 9～10 分鐘。
  之後實測仍不夠時，再用 `tc` 依流量分級（需 sudo）。
- 不採用「讀到哪個檔案才抓哪個」的唯讀 FUSE 檔案系統。它的好處是工作不必等複製、只讀一部分的工作只搬讀到的檔案；
  代價是要寫 FUSE 程式、完整訓練的第一個 epoch 受網路限制，以及讀到一半斷線的處理。

以下皆為提議：

- **S1** 資料集分兩層：原始資料層（大、幾乎不變）與標註層（label、CoT，小、常改、每人可各有一份）。
  工作同時掛載多個資料集，例如 `"datasets": ["vqa-images@1", "vqa-cot-alice@4"]`，
  在容器內是 `/datasets/vqa-images` 與 `/datasets/vqa-cot-alice`。目前已支援一個工作掛載多個資料集。
- **S2** 發布後的版本不可修改；內容改變就發布新版本。
- **S3** 提交時把 `名稱@latest` 解析成固定版本並寫進工作設定；重跑使用同一個版本。
- **S4** 正本放在 NAS（例如 `<NAS>/labflux/datasets/<名稱>/<版本>/`）；資料集目錄存在 Scheduler 資料庫，
  記錄名稱、版本、大小、檔案數、擁有者、指紋與來源。
- **S5** 常用的原始資料層可以標記成「每台 GPU 節點都保留」：發布後在網路空閒時預先複製，也不被 LRU 淘汰。
  以 1GbE 約 110 MB/s 計算，50 GB 每台約 7～8 分鐘。其餘版本照 S0，用到才複製。
- **S6** 還在修改的標註放在 NAS 上的工作區，只有擁有者能寫，工作直接從 NAS 讀取；改好後發布成版本。
- **S7** 前處理或 CoT 產生工作可以把產出發布成新的標註層版本，並記錄來源版本與產生它的工作。
  CoT 可以由批次工作呼叫推論 Gateway（M10）產生。
- **S8** 第一版不使用以內容 hash 儲存的檔案庫：分層之後只有標註層常改，整份複製的成本很低。
- **S9** NAS 上既有的資料夾可以原地登錄，只記錄指紋；發現內容改變時警告或拒絕使用。
- **S10** karma 掛上 NAS 之前，透過 kayle 以 HTTP 取得資料集版本（或處理 Q6）。

### 7.1 依資料位置排程（delay scheduling）

方向已認可，細節為提議：

- **L1** 對每個候選節點計算複製成本 = 該節點缺少的版本大小總和 ÷ 實測頻寬。
- **L2** 有完整副本的節點優先。
- **L3** 有副本的節點忙碌時，最多等待一段時間（預設等於複製所需時間）；超過後改排到其他節點，並在那裡複製。
- **L4** 複製在工作排隊期間進行，不佔 GPU；複製完成才配置資源。
- **L5** 重跑與被搶占的工作優先排回原節點。
- **L6** Dashboard 顯示判斷，例如「等待有副本的 kayle，剩 3 分鐘；之後改排 karma，需複製 50 GB」。

參考：Zaharia et al., *Delay Scheduling: A Simple Technique for Achieving Locality and Fairness in Cluster Scheduling*,
EuroSys 2010；Spark 的 `spark.locality.wait`。

## 8. 快速測試與 session（M9）

已決定（2026-11-15）：

- **T1** AI 工具一律在開發機本機執行；不把 AI 工具或整個終端機搬到 GPU 節點（那會讓 GPU 在 AI 思考時閒置卻被佔住，
  而且程式會在遠端被修改，需要雙向同步）。
- **T2** 指令路由：只有「執行程式」的指令送到租用的遠端 session（清單見 T7）；看檔案、改檔案與 `git` 等指令都留在本機。
  全部送遠端會讓 `git` 失敗、讓 `sed -i` 這類修改落在遠端副本，並讓每個小指令都多一次同步。
- **T3** 路由由 LabFlux 提供，不依賴特定 AI 工具的功能：使用者先執行 `labflux shell`，它在 PATH 最前面放入這些指令的替身，
  再從這個 shell 啟動 AI 工具；AI 照常輸入 `pytest`，不需要記得任何額外步驟。各 AI 工具是否保留這個 PATH 需要實測。
  bash 與 zsh 的啟動檔（conda、pyenv、venv）常把自己的目錄放到 PATH 最前面，所以 `labflux shell` 在啟動檔執行完之後、
  以及每次顯示提示字元之前，把替身目錄放回最前面；啟動時若有 alias 或 shell function 蓋住清單上的指令就印出警告（不移除）。
  其他 shell（例如 fish）只在啟動前設定一次 PATH，並印出提示。
- **T4** 命令改用「門鈴」送達：每個 Worker 維持一條主動連到 Scheduler 的長連線（WebSocket，仍然只由 Worker 連出去）。
  Scheduler 寫入命令後，透過這條連線送一個「有新命令」的通知；Worker 收到後照舊呼叫原本的 API 領取、處理、ack。
  另外保留每 5 秒一次的備援輪詢，以免連線剛好斷掉時漏掉通知。命令的可靠性仍然來自資料庫加 ack，
  長連線只負責讓命令更快送到，並讓閒置時的請求接近零（目前 2 台 Worker 閒置時每秒也有 8 次取命令的請求，
  每次都要拿資料庫的全域鎖）。
- **T5** 心跳維持定期送出（每 2 秒，逾時 10 秒），不改成事件觸發：判斷節點掛掉靠的是「該來的訊息沒來」，
  而連線可能看起來還開著、對方其實已經不在，這只有定期心跳抓得到。
- **T6** 快速測試的指令與即時輸出也走 T4 的長連線：開發機把指令送到 Scheduler，Scheduler 只在記憶體中轉給 Worker，
  輸出以同樣方式送回，不寫入資料庫。批次工作維持原本存進資料庫、可以重送的那條路。
  Worker 不必開 port，驗證只在 Scheduler 做一次，之後 M10 的 Gateway 也可以沿用。代價是多經過 Scheduler 一手
  （估計每個指令約 0.3 秒），而且 Scheduler 重啟時，進行中的互動指令輸出會遺失，需要重跑。
  不採用開發機以 SSH 直連 GPU 節點：延遲較低，但每台 Worker 都要開 port，帳號與金鑰也要另外管理。
- 資料集複製限速，見 S0a。
- session 工作目錄的同步：去程見 D4b，回程（寫回）見 D12。
- **T7** 送到遠端的指令：
  - 預設清單 `python`、`python3`、`pytest`、`torchrun`、`accelerate`、`deepspeed`、`nvidia-smi`，可在 `.labflux.toml` 增減。
  - `uv` 只送 `uv run`；`uv add`、`uv lock` 會改 `pyproject.toml` 與 `uv.lock`，留在本機。替身依子指令判斷。
  - 替身從目前目錄往上找 `.labflux.toml`（像 git 找 `.git`）；找到的那層是專案根目錄與快照範圍，
    找不到就直接執行本機的真正指令。
  - 要在本機執行時，用 `labflux local -- <指令>` 或完整路徑（例如 `/usr/bin/python3`）跳過替身。
  - 不用規則猜「這個指令很小、留在本機」：從指令看不出是否用 GPU，猜錯會讓 GPU 程式跑在開發機上。
    代價是 `python -c` 這類小指令也多約 0.3 秒；還沒有 session 時，第一個指令會先租 session，叢集滿載時要等。
    寫回（D12）讓會改檔案的腳本送到遠端也不會出錯。
  - 已知限制：`bash run.sh` 在本機執行，腳本內每個 `python` 各自送到遠端，彼此不共用環境變數；
    要整個腳本在遠端執行，使用 `labflux run -- bash run.sh`。
- **T8** Worker 的 outbox 改成有新事件或日誌時才喚醒上傳，不再每 0.25 秒檢查一次（Worker 程序內的通知，不經網路）。

已決定（plan M9）：

- 互動佇列排在批次工作之前；單次指令上限預設 60 秒。
- session lease 預設 10 分鐘（閒置時間，見 T9），每位使用者同時最多一個；同一個 session 一次只執行一個指令。
- 指令超時或 lease 到期時終止整個容器，回收資源並保留輸出。
- 可重用模式未通過驗收時，以每次獨立執行的模式交付並記錄限制。

已決定（2026-11-16，程式審查之後）：

- **T9** session lease 是閒置逾時：連續 10 分鐘沒有指令才回收（`session_lease_s`），每個指令開始與結束時都重新起算，
  指令失敗也算；有指令在執行時不回收。一直有指令在跑的 session 因此可以用超過 10 分鐘。
  backfill 以 session 目前的 lease 到期時間估計它何時釋放資源，所以排在 session 後面的隊首保留時段，會隨著每個指令往後移。
- **T10** 取消只停止指令：Ctrl-C 或客戶端斷線時，Worker 對該指令的 process group 送 TERM，寬限時間（`stop_grace_s`，預設 2 秒）
  後送 KILL；容器、工作目錄與 `.venv` 都保留，已寫出的檔案照常寫回，CLI 以 130 結束，下一個指令沿用同一個 session。
  單次指令的時限（預設 60 秒）與 `uv sync` 的時限維持終止整個容器，下一個指令租用新的 session。
  停不掉的指令（process group 無法送訊號，或送出後仍不結束）退回終止整個容器。
  代價是 session 映像需要有 POSIX `sh` 與可寫的 `/tmp`（指令透過 `sh` 啟動並記下 PID）；自行脫離 process group 的程序
  （`setsid`、daemon）不會被取消，留到 session 結束。
- **T11** 超過寫回上限的檔案只存在遠端 session：
  - Worker 在每個指令的結果裡回報 session 目前所有「只在遠端」的檔案（累計清單，不只這次指令的）；檔案在遠端被刪除、
    之後的指令改過它而且這次放得進寫回、或之後的快照帶來同一路徑的檔案時，才離開清單。
  - CLI 把清單寫到專案的 `.labflux/remote-files.txt`（路徑與大小；`.labflux/` 自帶 `.gitignore`，不進快照），
    清單有變動時在終端機印一行提示，沒變就不印；`labflux session files` 印出同一份清單。Worker 不再另外送提示。
  - 這些檔案在送到遠端的指令裡以同一個路徑讀得到，session 結束時跟著工作目錄刪除，清單也一併移除。
    要保留只能寫到 `/outputs`（session 結束時上傳到 Scheduler，上限與批次工作相同）。
  - AI 工具得知「檔案在遠端」的主要管道是剛執行完的指令輸出裡的那一行；清單讓它在提示離開上下文之後還查得到。
- **T12** 同一個 session 一次仍只執行一個指令，但第二個同時送出的指令不再立刻失敗：CLI 每秒重試一次、每次重新打包快照，
  最多等 `.labflux.toml` 的 `[session] busy_wait_s`（預設 120 秒，0 表示不等）。AI 工具會平行送出指令；等待中的指令因此
  看得到前一個指令寫回的檔案。先後順序不保證。
- **T13** 排隊中的 session 靠客戶端的詢問維持：CLI 等待時每 0.25 秒查詢一次；超過 `session_queue_timeout_s`（預設 30 秒）
  沒有任何查詢（CLI 被強制結束）就取消這個 session，不讓它一直佔著互動佇列的隊首。

考慮過但不採用的做法（T11）：

| 做法 | 不採用的原因 |
|---|---|
| 只印提示，不留清單 | 提示離開 AI 的上下文之後，就沒有任何紀錄可查 |
| 在本機放同名的佔位檔 | 打包規則一出錯，佔位檔就會蓋掉遠端的真檔；AI 讀到假內容也可能誤判訓練失敗。失敗的後果最重 |
| 在本機放說明檔（例如 `model.pt.labflux-remote`） | 專案目錄多出散落的檔案，session 結束要逐一清理，而且仍然需要清單記錄放了哪些。實測 AI 工具（9.14）時若常漏看遠端檔案，再疊在清單之上 |

提議：

- session 已在執行時，每次 `labflux run` 的額外延遲目標為 1 秒以內；venv 在每次租用時只建一次。
- 目前命令輪詢間隔 0.25 秒，加上日誌 outbox，實測推算每個互動指令多 0.4～0.75 秒；改用門鈴（T4）後可省掉輪詢的等待。

## 9. 模型服務與推論 Gateway（M10）

已決定（plan M10）：

- 模型設定包含名稱、映像、CPU／RAM／GPU、啟動參數與快取位置；後端使用 vLLM 的 OpenAI 相容介面。
- 同一模型的並行啟動請求合併成一次配置與啟動。
- 冷啟動請求最多等待 120 秒，未就緒時回傳可重試的錯誤；健康檢查通過才導流；啟動超過 300 秒視為失敗並清理。
- 記錄進行中的請求數與最後活動時間；閒置 5 分鐘後停止；有工作在等資源時，可在閒置 60 秒後提前回收。

提議：開發節點上的 agent 以 `OPENAI_BASE_URL` 指向 Gateway，並以個人 token 驗證。

## 12. 之後的擴充

以下項目在第一版之後、時間允許時才做。這裡只記錄要解決的問題與目標，實作方式之後再討論。

### E1 Scheduler 所在節點故障

目前整個系統只有一個 Scheduler，跑在 kayle 上；資料庫、程式快照與輸出也都只存在 kayle 的磁碟上。
M6.6 處理的是 Scheduler 程序重啟、可以在原機器恢復的情況；E1 處理的是整台節點故障，Scheduler 無法在原機器恢復的情況。

kayle 故障時，現在會發生的事：

- 使用者無法提交、查詢或取消工作，Dashboard 也打不開；排隊中的工作不會被派送。
- 其他節點上已在執行的容器會繼續跑到結束或時限；Worker 把事件、日誌與輸出留在本機 outbox，等連得上 Scheduler 再重送。
- kayle 本身也是 Worker，上面的工作會跟著中斷。
- kayle 的磁碟無法復原時，工作紀錄、程式快照與輸出都會遺失。

擴充的目標：

- **E1.1** Scheduler 所在節點故障後，由其他節點接手排程；使用者不必修改設定，就能繼續提交、查詢與取消。
- **E1.2** 接手後的狀態與故障前一致：已提交的工作不遺失，同一個 attempt 不會在兩處執行，資源不會超配。
- **E1.3** 其他節點上執行中的工作不受影響，結果照常回報到接手的 Scheduler。
- **E1.4** 從偵測到故障到恢復服務的時間有上限，並在 Dashboard 與 CLI 上看得到目前由哪個節點負責排程。

### E2 程式也放進 LabFlux 的檔案系統（路線 2）

資料集的 lazy 檔案系統完成後，再評估是否擴充成可以寫入的專案目錄：每台機器看到同一份專案，
第一次打開檔案時才抓到本機，換機器時直接打開就是最新的，不必 git push／pull。

- 前提：同一個專案同時只有一台機器能寫（D3a），用 lease 保證。
- 要處理：關檔時寫回中央、rename、只寫了一半的檔案、當機恢復；`.venv` 仍放在本機。
- 風險：AI 工具與 `git status` 會頻繁查詢檔案狀態，每次都經過 FUSE，可能明顯變慢。
- 工作仍使用送出時的快照（D4），不直接讀這個目錄。

### E3 保存區同步到其他機器

目標：讓 6.1 的保存區不再只能在原本那台機器上使用。可能的做法：

- 要用它的工作排不進原本的節點時，把整個保存區複製到另一台，再排到那台：和資料集的整份複製（S0、S0a 限速）共用機制，
  P2 的硬性親和就變成有上限的等待（同 7.1 的 delay scheduling）。
- 使用者手動複製：`labflux persist copy <名稱> --to <節點>`。
- 定期備份到 NAS，降低 P7 節點故障時的損失。
